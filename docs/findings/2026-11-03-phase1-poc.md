## 1–3. Codex (official, subscription-backed)

- **Integration chosen: `codex app-server`** — the official JSON-RPC-over-stdio interface used by
  Codex's own rich clients. Docs: <https://learn.chatgpt.com/docs/app-server>. The TypeScript
  `@openai/codex-sdk` exists but does not document login, approvals or sandbox options; app-server does.
- **Auth:** `account/login/start` with `type: "chatgpt"` returns an `authUrl`; app-server hosts the
  local callback. With `cli_auth_credentials_store = "keyring"` the token went to the macOS Keychain —
  no `auth.json` was written.
- **Isolation:** the companion uses its own `CODEX_HOME`
  (`~/Library/Application Support/ClaudeGPTCompanion/…`), so the user's normal Codex config is untouched.
- **Threads:** `thread/start` (accepts `cwd`, `sandbox`, `approvalPolicy`, `developerInstructions`),
  `turn/start`, `thread/resume`. Streaming via `item/agentMessage/delta`, ending with `turn/completed`.
- **Caveat — read-only is write-only protection.** In 0.166.0 `SandboxPolicy.readOnly` has only
  `networkAccess`; it blocks writes but **allows reading any file on disk**. So the sandbox alone cannot
  keep secrets private. The PoC therefore:
  1. disables Codex's own tools: `[features] shell_tool = false, unified_exec = false`, plus
     `apps`, `plugins`, `browser_use`, `computer_use`, `image_generation`, `multi_agent`, `hooks`, `memories`;
  2. uses `sandbox: "read-only"` and `approvalPolicy: "untrusted"`, and the client **declines** every
     `item/commandExecution/requestApproval` / `item/fileChange/requestApproval` and errors every other
     server request;
  3. gives Codex one MCP server of our own (`poc/codex/readonly-mcp.mjs`) restricted by `enabled_tools`
     to `list_dir`, `read_file`, `search`, `git_status`, `git_diff`, jailed to one repo root
     (realpath check, deny-list for `.env*`, keys, `.ssh`, `.git` internals, `node_modules`, …).
- **Bug found in the PoC jail:** it resolves the path before the "outside repository" check, so a
  missing out-of-repo file says "not found" instead of "outside repository" — that leaks whether a file
  exists. The real implementation checks containment first.
- **Not yet tested end to end:** the `.env` deny rule. Creating a fake `.env` was blocked by the
  work-repo guard of the session that built this PoC; it will be covered by unit tests instead.
- **MCP tool allowlist:** `enabled_tools` / `disabled_tools` per `[mcp_servers.<name>]` are documented
  (<https://developers.openai.com/codex/mcp>). That an *excluded* tool is really hidden is not yet
  proven — Phase 4 test for the Jira server.
- Codex does **not** include ChatGPT's personal memory or the ChatGPT web UI features.

## 4. Claude Desktop session context

Re-verified on Claude Desktop 4.16336.0 (keys inspected, no content copied):

- **Desktop records:** `~/Library/Application Support/Claude/claude-code-sessions/<org>/<account>/local_<id>.json`
  — keys include `sessionId`, `cliSessionId`, `cwd`, `originCwd`, `branch`, `title`, `lastFocusedAt`,
  `lastActivityAt`, `isArchived`, `model`.
  **Changed:** `lastAssistantCliSessionId` now appears in only 4 of 249 records — do not rely on it.
- **Transcripts:** `~/.claude/projects/<cwd with every non-alphanumeric char → "-">/<cliSessionId>.jsonl`.
  Record `type`s seen: `user`, `assistant`, `attachment`, `custom-title`, `agent-name`, `last-prompt`,
  `file-history-snapshot`, `queue-operation`, `api-request*`, … Records carry `uuid`, `parentUuid`,
  `isSidechain`, `toolUseResult`, `cwd`, `gitBranch`, `timestamp`.
- **Subagents:** `~/.claude/projects/<project>/<cliSessionId>/subagents/`.
- **Running sessions:** `~/.claude/sessions/<pid>.json` with `sessionId` (= desktop `cliSessionId`, 3/3
  matched), `status` (`busy` / `idle`), `pid`, `entrypoint: claude-desktop`.
  **Sensitive:** this directory also holds `*.key` files and a `messagingSocketPath`. The companion must
  read only `<pid>.json` and never open the keys or the socket.
- **Focus:** the record with the highest `lastFocusedAt` was the session actually in front — usable as
  "currently focused", with a manual picker/pin as the override.

## 5. Terminal context

- Bash tool calls, stdout/stderr and exit status are in the transcript (`tool_use` + `toolUseResult`).
  This is the v1 terminal source.
- **Live PTY: not supported.** Claude Desktop exposes no documented read-only terminal stream. The only
  socket seen (`messagingSocketPath`) is a peer-messaging channel; connecting to it could send input or
  consume messages, so the companion will not touch it. Transcript context lags a running command until
  its result is written — documented limitation.

## 6. Speech

- `SpeechAnalyzer` + `SpeechTranscriber` (macOS 26+): available, 45 supported locales, 9 English locales
  installed. `SFSpeechRecognizer` on-device recognition also available as the fallback for macOS 15.
- `AVSpeechSynthesizer`: 41 English voices (0 enhanced/premium installed — users can download them in
  System Settings).

## Toolchain facts

- **No full Xcode** — only Command Line Tools. `swift build` / `swiftc` work (the speech check compiled
  and ran), but **`swift test` fails** in the Testing framework module build. Consequence: keep logic in
  the TypeScript service (testable with `node --test`) and keep Swift a thin UI. Installing Xcode (free)
  unlocks Swift unit tests later.

### Q1 — Exact flag keys, and where the self-check should read them
- Ran: `node spikes/m1/p1-flags.mjs`
- Observed: all 11 keys exist (`shell_tool`, `unified_exec`, `apps`, `plugins`, `browser_use`,
  `computer_use`, `image_generation`, `multi_agent`, `hooks`, `memories`, `view_image`).
  `config/read` → `config.features`: all 11 `false`. `experimentalFeature/list` → `enabled: false` for 10,
  but `unified_exec` `{stage:"stable", enabled:true, defaultEnabled:true}` (`shell_tool`, also stable,
  shows `false`). `web_search: "disabled"`. Layers: user `config.toml` + system `/etc/codex/config.toml`.
- Verdict: changed: keys confirmed, but the two sources disagree on `unified_exec`. **Unresolved:** this
  probe cannot tell whether the list value is a stale default or an effective override. The self-check
  must read `config/read` (all off) **and** the list, and treat list `unified_exec: true` as a known
  discrepancy to show, not as a pass. → spec §7.1.1, §7.1.5 updated

### Q2 — Does an empty thread `cwd` keep repo `AGENTS.md` out?

### Q3 — Does `enabled_tools` hide a write tool? What else can the model reach?
- Ran: `node spikes/m1/p3-enabled-tools.mjs`, then `node spikes/m1/p8-hardened-tools.mjs` and
  `node spikes/m1/p9-exec-surface.mjs`
- Observed:
  - p3: `mcpServerStatus/list` lists `["read_file"]` (names unprefixed); `write_file` never called.
  - p8 (hardened config): asked to `touch` a file → no `commandExecution` item, no approval request, no
    file. Asked to use `apply_patch` → a `fileChange` item and an `item/fileChange/requestApproval`
    request; our decline → status `declined`, no file. The model said it called `apply_patch` through
    `functions.exec`; the `fileChange` item still surfaced. Despite the flags it lists at least
    `functions.exec`, `functions.wait`, `functions.request_user_input(_async)`, `clock.sleep`,
    `collaboration.*` (spawn/send/wait/list/interrupt agents) and `apply_patch`; the reply was cut at
    300 characters (ends `tools.create_g…`), so the list is incomplete. M4 captures the full list.
  - p9: asked to print a canary file outside the cwd via `functions.exec` → no `commandExecution` item,
    no server request, canary not in reply. The model said `functions.exec` has no filesystem access.
- Config-key search (read-only, in the installed `@openai/codex` 0.166.0: `codex --help`,
  `codex features list`, strings in the bundled binary): **no key found that removes `apply_patch`**
  (`include_apply_patch_tool` absent; `apply_patch_tool_type` appears only as a model-catalog field).
  Candidates, unverified (to try in M4, CodexHost): `features.code_mode_host` (stable, default on; a `codex-code-mode-host` binary
  ships, and `functions.exec` looks like code mode), `features.sleep_tool` (likely `clock.sleep`). No
  key found for `collaboration.*` beyond `multi_agent` (already off) or for `request_user_input`.
- Verdict: changed. `enabled_tools` works for a local MCP server. But `apply_patch` cannot be turned off
  by the flags we set, so "no writes" rests on declining every `fileChange` approval, the read-only
  sandbox and the runtime guard. The exec surface is **inconclusive**: `functions.exec` calls do not
  surface as items, the model declined on its own, one run only. This does not show that a shell is off
  or that exec cannot read files. → spec §7.1.1, §7.1.4, §7.1.6, §7.1.8, §11, §16 updated

### Q4 — Can one app-server bind each thread to its own root (option A)?
- Ran: `node spikes/m1/p4-root-binding.mjs`
- Observed: two config shapes. Dotted: the probe set only `mcp_servers.fake.env.FAKE_ROOT`. Nested:
  the probe restated the whole `env` table (`FAKE_TOOLS`, `FAKE_LOG`, `FAKE_ROOT`). Both: thread A
  `sawOwnRoot true / sawOtherRoot false`, thread B the same. `distinctMcpProcesses: 4` (one per thread
  per shape). Whether the nested shape merges with or replaces the base `env` is unknown, so M4 uses the
  dotted form or restates the whole `env`. First run failed: under `approvalPolicy: "untrusted"` every
  MCP tool call sends `mcpServer/elicitation/request`, and an errored reply rejects the call. Replying
  `{action:"accept", content:null, _meta:null}` (to every elicitation, unchecked) fixed the probe.
  `thread/resume` with the override was not tested.
- Verdict: confirmed option A for `thread/start`; `thread/resume` is an M4 integration test, option B
  stays the fallback until it passes. Changed: the companion must **accept** elicitation only when the
  `serverName` is allowlisted and the request is a tool-call approval for an allowlisted tool, and
  decline everything else, including `url` mode and form elicitations. → spec §2, §7.1.4 updated

### Run 2: narrow metadata plus metadata-only rules for the symlinks dyld follows

The fix:
- At discovery, `toolchain.ts` reads the Mach-O load commands (`LC_LOAD_DYLIB` and related, plus
  `LC_RPATH`) of Node and each loaded non-system library. These are the paths as dyld is told to load them.
- It walks every absolute one component by component and records each symlink hop (`Toolchain.metadataPaths`).
  Links too broad to name, such as `/tmp` and `/var`, are left out.
- In narrow mode the profile allows `file-read-metadata` on each hop as a `literal`. Never `file-read-data`,
  never a `subpath`.
- On this Mac that is 34 links: the `/opt/homebrew/opt/<formula>` links and the version-named dylib links
  inside each keg.

### Limits of the symlink-hop rules

- Only absolute install names and rpaths are walked. `@rpath/…`, `@loader_path/…` and
  `@executable_path/…` entries are not expanded, so a symlink reached only through one of those gets no
  metadata rule. If a Node build needs one, it fails closed (Node does not start), it does not widen the
  profile.
- Measured on one build only: Homebrew arm64 Node v26.7.0, on this Mac. The `companiond-macos` CI job
  (`macos-26`, `actions/setup-node` Node 24) passes the same Seatbelt suite, but it was not run through
  `scripts/measure-profile.ts`, so its variant table is not recorded here.
